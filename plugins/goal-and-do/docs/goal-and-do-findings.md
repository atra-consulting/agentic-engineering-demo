### What the spike sets for Tasks 3 to 5

Where this departs from the plan, the plan changes before Task 3; where it departs from the design doc, it is folded in at Task 7.

1. **Goal start.** The start and `next` start their goal through `$.clock.after(0, ...)` from `command.run` (question 1). The start reply has no "Send any message" sentence. `pendingGoal` stays for the fallback only: a refused `clock.after` start leaves the goal pending for the next main-loop `turn.complete`, with the toast and the `/goal` line to paste.
2. **Chaining.** Build, Test and PR chain from `turn.complete`, which fires after the evaluator's verdict, so the phase file is final when the mod reads it (question 3).
3. **The turn cap moves to `classic.Stop`.** A goal's turns are one main-loop turn, so `turn.complete` can't count them (4a). The mod counts goal turns in a `classic.Stop` hook, only while its own goal is set (a Stop fires on plain turns too). At the cap it returns `{}` without `next`, which ends the loop; the `turn.complete` that follows marks the phase `capped` and runs `/goal clear`. `countTurn` is called from `classic.Stop`; the evaluator's own cap is best effort (it overran in 7b). A turn in the caps and the usage table is a goal turn.
4. **`stop` mid-goal.** `/goal clear` can't run while the loop runs (4c). `stop` sets `pendingClear`; the next `classic.Stop` cuts the loop the same way, and `turn.complete` clears the goal. For `stop` to run while a goal's turn runs, its command needs `immediate: true` (not tested in the spike; Task 5 checks it). Esc interrupts at once in any case.
5. **A goal that ends without `status: done`.** Besides met and capped, a goal can end "could not be achieved" (the evaluator judged it out of reach, 6 and 10) or "paused" (the engine's cap of 9 Stop blocks in a row without a tool call, 7b). In both the goal may stay set. On every main-loop `turn.complete` that ends its phase, the mod clears the goal (or the next goal replaces it, 4b), reads the phase file, and treats anything but `done` as stuck: `blocked` with the file's reason, or with the evaluator's last reason from `classic.Stop` when the file gives none.
6. **Dialogs.** The gate, stuck, push and rule dialogs open from `turn.complete` without blocking, and their answers' continuations start the next goal directly (5b, 5d). The `{ text }` a `turn.complete` hook returns shows beneath the answer (5c). The gate text drops "`next` approves directly".
7. **A fresh context per phase.** `/clear` from `turn.complete` works and leaves no memory of the previous phase (7a); compaction doesn't (7b). So the mod runs `/clear` before each phase's goal, and the design doc's shared-context deviation goes. `/clear` empties `$.state`, so the mod writes the run back into its atom right after it (from its module copy, else `run.json`). Costs: each phase rebuilds its context, and the person loses the previous phase's transcript on screen.
8. **Usage.** Rows come from main-loop and subagent `turn.complete`, as planned. The working model matches `/usage` (6). The `/goal` evaluator's tokens, and in auto mode the permission classifier's, both on Haiku, reach no event the mod sees: 22 percent of the spike's cost. The footer says "not counted", and Task 7's count check compares per model with `/usage`, expecting the Haiku row to be missing. An interrupted turn does carry usage (13), so the footer drops "Interrupted turns count nothing".
9. **Restore.** `$.state` is empty after a restart (13) and after `/clear` (7a); `run.json` is the source on `session.start`, as planned. After `--continue` the old goal is still set but idle; `next` clears it before it reruns the phase.
10. **Goal texts.** The 500-character test stays (600 accepted, question 11). Each goal text names what to show, since the evaluator wants evidence of every part of the condition (11) and blocks without it.
11. **Command replies are model context** (1, side note): short and factual.
12. **Code shape.** Helpers that take `$` sit at the top of `register.tsx` (the validator's rule); `types/index.d.ts` declares state in `declare module 'claude-code' { interface PluginState { ... } }`.
13. **Tests.** The register test of the learning path stays (question 12).
14. **No skill sets its own goal** (questions 8 and 9): Key decision 1 stands, and there is no choice for the author before Task 3.

Design doc open questions answered here: the evaluator and the turn cap (best effort; a turn is a goal turn), `/goal`'s argument limit (at least 600), and whether the evaluator's tokens reach `turn.complete` (no).

| 40,000 characters of output | not set | `<persisted-output>` | adds `persistedOutputPath`, `persistedOutputSize`; `stdout` cut at 30,000 |
| A timeout of 3 s on a 30 s command | not set | `Command did not complete within its 3s timeout and was moved to the background (ID: …)` | `backgroundTaskId`, `timedOutAfterMs: 3000` |
| `run_in_background: true` | not set | `Command running in background with ID: …` | `backgroundTaskId` |
| Refused in "don't ask" mode | `true` | `Permission to use Bash has been denied because Claude Code is running in don't ask mode.` | none |
| A bare `sleep 30` | `true` | `<tool_use_error>Blocked: standalone sleep 30.` | none (Claude Code blocks it before it runs) |

- **A background task's end reaches the mod** as `prompt.submit` with `origin.kind: "task-notification"`. Its `text` holds `<task-id>`, `<tool-use-id>` (the call that started it), and `<status>completed</status>` or `<status>failed</status>`. A Monitor's expiry arrives the same way, with no `<status>`.
- **Not seen headless:** the transcript row's `task` prop (no screen draws in `-p`), an interrupt with Esc, and the text of a refusal at an interactive permission prompt. The demo session checks them.

## Request for the Claude Code team: the "moved to the background" line

Checked at Claude Code 2.1.316 on November 1, 2026, for the change CH-20261101-scan-each-commit-and-push-for.

- **Result:** no hook reaches the line "Your conversation moved to the background" that Claude Code prints when a session is moved to its background list. `session.attach` and `session.detach` cover remote clients (the terminal's attachment raises nothing). The `InfoNotice` render component is the status line under the logo. The background list screen draws the line as plain dim text outside every render component. So nothing is built to restyle it.
